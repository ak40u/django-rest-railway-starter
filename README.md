# Django REST Framework starter for Railway

Django 6 and DRF on Postgres, with a generated signing key and migrations in the
pre-deploy step.

## Why this exists

The Django REST template on Railway deploys a repository last touched in
September 2023 — Django 4.2, DRF 3.14, `psycopg2`. None of its deployments report
healthy. But the version drift is not the worst part.

**Its `SECRET_KEY` is a literal, committed into the template.** Every project
deployed from it shares the same Django signing key. Anyone who reads that
template — it is public — can forge session cookies and password-reset tokens
against every site created from it.

Here `SECRET_KEY` is generated per deployment, and `config/settings.py` reads it
with `os.environ["SECRET_KEY"]` rather than `os.environ.get(..., "fallback")`. A
missing key stops the app at startup instead of silently falling back to a shared
default — which is exactly how a template ends up shipping one key to everybody.

## What's in here

| File | Why it exists |
|------|---------------|
| `config/settings.py` | Environment-driven settings: database URL, allowed hosts, HTTPS behind a proxy |
| `api/` | A `Note` model, a DRF ViewSet, and a health endpoint that touches the database |
| `gunicorn.conf.py` | Binds `PORT` at runtime |
| `railway.json` | Pre-deploy migration, health check, restart policy |
| `requirements.txt` | Current Django, DRF, `psycopg` 3, WhiteNoise |

Four settings worth understanding before you extend this:

- **`SECURE_PROXY_SSL_HEADER`.** Railway terminates TLS at its proxy. Without
  this, Django thinks every request is plain HTTP and builds `http://` redirects
  that break the login flow.
- **`CSRF_TRUSTED_ORIGINS`.** Django checks the `Origin` header on unsafe
  methods; a proxied HTTPS request fails that check unless the scheme is listed.
- **`ALLOWED_HOSTS`** is built from `RAILWAY_PUBLIC_DOMAIN`, which the platform
  sets at runtime, so it is correct without you pasting your domain anywhere.
- **Migrations run in `preDeployCommand`**, after the build and before the new
  version takes traffic — the build has no database to connect to. `predeploy.sh`
  retries only while Postgres is still refusing connections, which is what the
  first deploy of a project looks like when the database is still starting;
  Railway does not retry a failed pre-deploy command on its own.

## Endpoints

| Method | Path | Does |
|--------|------|------|
| GET | `/api/health/` | Runs `SELECT 1`; 503 when Postgres is unreachable |
| GET | `/api/notes/` | Paginated list |
| POST | `/api/notes/` | Creates a note — requires authentication |
| — | `/admin/` | Django admin |

The default permission is `IsAuthenticatedOrReadOnly`: anyone can read, only
authenticated users write. Change `REST_FRAMEWORK["DEFAULT_PERMISSION_CLASSES"]`
if that is not what you want.

Create the first user after deploying:

```bash
python manage.py createsuperuser
```

## Run locally

```bash
python -m venv .venv && .venv/bin/pip install -r requirements.txt
export SECRET_KEY="anything-for-local-dev" DEBUG=true
.venv/bin/python manage.py migrate
.venv/bin/python manage.py runserver
```

Without `DATABASE_URL` it falls back to SQLite, so local work needs no database.

## Configuration

| Variable | Required | Purpose |
|----------|----------|---------|
| `SECRET_KEY` | yes | Django signing key — generated by the template |
| `DATABASE_URL` | yes in production | Postgres connection string |
| `DEBUG` | no | `false` by default |
| `ALLOWED_HOSTS` | no | Extra hostnames, comma-separated |
| `CORS_ALLOWED_ORIGINS` | no | Front-end origins, comma-separated |
| `WEB_CONCURRENCY` | no | Gunicorn workers, defaults to 2 |
